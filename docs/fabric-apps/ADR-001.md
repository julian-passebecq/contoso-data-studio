# ADR-001 · Model source of truth and local backend for Fabric-style apps

Status: accepted · 2026-10-06 · package FABRIC-APPS-LAB

## Spike (30 min, offline, no sign-in)

1. **`@microsoft/rayfin-core@1.36.2` installs from npm and works offline.** The decorators are TC39
   standard decorators (TypeScript 5, `lib: ESNext.Decorators`, no `experimentalDecorators`). Its own
   `SchemaAnalyzer` + `ConfigGenerator` (export `@microsoft/rayfin-core/analysis`) compile our classes
   into the Data API Builder config Rayfin deploys (tables, `{prop}_id` foreign keys, constraints,
   permissions with compiled policies), with no CLI, login or network. `serializeCheckToAst` gives the
   policy as an AST we can evaluate locally.
2. **Rayfin's pure local mode is not usable here.** It is `rayfin dev --provider docker`, a preview behind
   `RAYFIN_FEATURE_FLAGS=docker-local-dev`. It needs Docker Desktop running (not running on this PC), the
   `mcr.microsoft.com/mssql/server:2025-latest` image, and `ghcr.io/microsoft/project-rayfin/webservice:cli-<version>`,
   which answers `UNAUTHORIZED` to an anonymous pull. Not something CI or a fresh clone can rely on.

Findings that change the plan:
- 1.36.2 types `@role()` to the built-in roles only (`authenticated`, `anonymous`; package doc
  `permissions.md`). App roles `finance` and `executive` are therefore expressed as policies on the `role`
  claim: `@authenticated('read', { policy: (c, i) => c.role.eq('executive').or(c.email.eq(i.owner_email)) })`.
  Claims are only `sub`, `email`, `role`, and policies cannot join, so the department row policy uses a
  denormalised `owner_email` column on Forecast and Actual.
- The 1.36.2 package docs (`rayfin-guide/data/graphql.md`) document the client as
  `client.data.<Entity>.select([...]).where({...}).orderBy({...}).execute()`, plus `findById`, `create`,
  `update(filter, patch)` and `delete`. The Learn article shows `client.data.<plural>.query().select().execute()`.
  Our local client offers both shapes.

## Decision

**Use the real Rayfin decorators as the model source of truth, plus our own local adapter.**
- `apps/fabric-app-lab/rayfin/data/` holds the entities and `schema.ts` in Rayfin's layout. They carry over unchanged.
- `npm run export-model` writes `rayfin/generated/dab-config.json` and `model.json`; the Python backend
  only reads `model.json` (CI checks it is not stale).
- Everything else is our adapter, named `local*` and listed in the port checklist: the REST transport, the
  local client, fake users in place of Entra ID, the mirror worker and the policy evaluator.

**Operational store: SQLite**, not DuckDB. Reasons: row-at-a-time OLTP writes and short transactions are
what SQLite is built for (Fabric's operational store is SQL Server-family, also a row store); it is in the
Python standard library; WAL lets the API write while DuckDB attaches the same file read-only to mirror it;
and a second DuckDB file would compete with the DuckLake catalog connections the API already opens.
DuckDB stays the analytics engine (mirror target and SQL endpoint), as in Fabric where the SQL DB and OneLake
are separate engines.

Not Rayfin API, local only: the HTTP routes under `/api/fabric-apps/*`, the `X-Local-User` header, the
mirror and trace endpoints, and the `owner_email` consistency check done in the adapter.
